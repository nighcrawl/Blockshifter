# Assets et télémétrie d'un Module déclenchés au rendu effectif, pas par détection dans `post_content`

Remplace, dans ADR-0010, le point « Détection des features ». Jusqu'en 0.3.0, les assets front d'un Module et le flag télémétrie `seen` étaient décidés sur `wp_enqueue_scripts` via `has_block()` sur `$post->post_content`. Le test manuel Query Loop a montré que ça ne voit jamais un Target Block rendu depuis un template (Query Loop de l'accueil, archives, template parts) : le HTML était bien transformé par `render_block`, mais Splide/Masonry n'étaient jamais chargés et l'usage n'était jamais compté. Effet de bord inverse : la seule présence d'un `core/group` ou `core/post-template` chargeait les assets de tous les Modules, même inactifs.

Décision : `Blockshifter_Render::dispatch()` déclenche l'action `blockshifter/module_rendered` (argument : le Module) chaque fois qu'un Module transforme réellement un bloc. `Blockshifter_Assets::enqueue()` et `Blockshifter_Telemetry::record_feature_usage()` s'y accrochent ; la détection par `post_content` est supprimée. Enqueuer pendant le rendu est sûr même avant l'enregistrement des handles (un thème bloc rend son template avant `wp_head`, donc avant `wp_enqueue_scripts`) : `WP_Dependencies` garde un handle enqueué avant son enregistrement et l'enqueue dès qu'il est enregistré. Thème classique : le contenu est rendu après `wp_head`, les styles enqueués tard sont imprimés en footer par WordPress — accepté.

Alternative rejetée : scanner aussi le template résolu (`get_the_block_template_html()` / `$_wp_current_template_content`) avec `has_block()`. Couvre les templates mais pas les cas dynamiques (template parts, patterns synchronisés, blocs rendus via REST), garde le sur-chargement des assets de Modules inactifs, et duplique une information que le rendu connaît déjà avec certitude.
