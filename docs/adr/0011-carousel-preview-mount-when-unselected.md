# Carousel Editor Preview monte/détruit Splide sur le vrai DOM, seulement quand le bloc n'est pas sélectionné

Le rendu front (`class-carousel-transform.php`) restructure une string HTML statique une seule fois : il insère `.splide__track > .splide__list` et tague les enfants directs `.splide__slide`. Dans l'éditeur, le contenu du bloc est un arbre React vivant (InnerBlocks, re-rendu à chaque frappe), et Splide a structurellement besoin d'au moins deux niveaux de DOM en plus du bloc lui-même (`.splide__track` pour le masquage, `.splide__list` pour la translation) — son option `classes` permet de renommer les classes qu'il cherche, pas de faire l'économie de ces deux niveaux. Composer cette structure en JSX autour de `<BlockEdit {...props} />` ne marche pas : `editor.BlockEdit` ne permet d'ajouter du JSX qu'à côté de `BlockEdit`, jamais à l'intérieur de son arbre (InnerBlocks reste hors d'atteinte à la profondeur voulue) — **une première version de cette ADR proposait cette approche ; elle s'est révélée irréalisable et est abandonnée ici.**

Décision : monter un vrai Splide sur le DOM réel du bloc (retrouvé via `#block-{clientId}`, même technique que le Module Masonry), mais uniquement quand le bloc **n'est pas sélectionné** (`isSelected === false`) — et détruit dès qu'il redevient sélectionné, avant que Gutenberg n'ait une chance de modifier ses enfants (ajout/suppression/réordre d'image). Ça élimine le cas de conflit réel : React ne réconcilie les enfants directs d'une Gallery/Group qu'en réponse à une action d'édition, qui exige que le bloc soit sélectionné.

**Correction post-implémentation** : Splide (v4) ne construit jamais lui-même sa structure `.splide__track > .splide__list` — il lève une erreur (`A track/list element is missing`) si elle n'existe pas déjà, contrairement à l'hypothèse initiale de cette ADR. C'est précisément pour ça que le PHP l'insère explicitement (`insert_splide_track()`). Côté éditeur, `preview.js` fait donc cette même insertion lui-même (`wrapForSplide()`/`unwrapForSplide()`) : les enfants réels du bloc sont **reparentés** (jamais recréés) dans les wrappers `.splide__track`/`.splide__list` juste avant `splide.mount()`, et remis à plat juste avant/pendant la destruction. Comme ce sont les mêmes nœuds DOM tout du long, les références de React vers ces nœuds restent valides pendant le déplacement — seul le moment où React tenterait de réconcilier leur position (ajout/suppression/réordre, qui exige la sélection) reste le point de rupture évité par la contrainte "jamais pendant la sélection".

Limite assumée : la List View ou une action déclenchée depuis un autre bloc peuvent en théorie modifier les enfants d'un bloc Carousel non sélectionné. Le risque résiduel est jugé acceptable pour le MVP 0.3 plutôt que de sacrifier la fidélité Splide réelle (alternative rejetée : un carousel CSS "maison" en scroll-snap, sans restructuration DOM donc sans risque, mais qui perd les vraies options Splide et devient exactement le "faux Carousel" que la spec voulait éviter).
