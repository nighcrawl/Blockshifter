# Carousel Editor Preview compose la structure Splide en JSX, ne laisse jamais Splide muter le DOM

Le rendu front (`class-carousel-transform.php`) restructure une string HTML statique une seule fois : il insère `.splide__track > .splide__list` et tague les enfants directs `.splide__slide`. Dans l'éditeur, le contenu du bloc est un arbre React vivant (InnerBlocks, re-rendu à chaque frappe) — laisser Splide faire sa restructuration DOM habituelle (déplacer des nœuds hors de l'arbre que React possède) provoquerait des erreurs de réconciliation (`removeChild` sur des nœuds que React croit toujours siens) au rerender suivant.

Décision : le composant `preview.js` du Module Carousel compose lui-même en JSX la structure `.splide > .splide__track > .splide__list` autour de `<BlockEdit {...props} />` — React reste propriétaire de cette structure dès le premier rendu. Splide est configuré via son option `classes` pour reconnaître les wrappers natifs déjà posés par Gutenberg (ex. `.wp-block-image`) comme ses slides, plutôt que d'injecter une classe `splide__slide` sur les enfants InnerBlocks. Ça s'appuie sur la garantie `useBlockProps()` de Gutenberg : le wrapper d'un bloc en édition porte les mêmes classes que son `save()`, donc les classes natives sont un point d'ancrage stable des deux côtés (front et éditeur).

Alternative rejetée : DOM impératif classique (ref + `useEffect` laissant Splide restructurer le DOM comme il le fait par défaut) — plus proche du comportement Splide "stock", mais fragile face aux re-renders React et sans bénéfice réel puisque l'édition native (sélection, InnerBlocks) doit de toute façon rester intacte.
