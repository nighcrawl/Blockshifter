# Masonry en CSS Grid + calcul JS des spans, pas de lib tierce ni de CSS columns

Le Module Masonry cible `core/gallery` et `core/group` (comme Carousel). Le layout est du CSS Grid natif (`grid-template-columns` + `grid-auto-flow: dense`), pas du CSS `columns` (multi-colonnes) : `columns` produit un vrai masonry 100% CSS mais remplit les colonnes verticalement (item 1, 2, 3 empilés avant de passer à la colonne suivante), ce qui casse l'ordre de lecture naturel gauche-à-droite du contenu. Comme CSS Grid seul ne fait du vrai masonry (packing par hauteur réelle) qu'avec `grid-template-rows: masonry` (support navigateur encore expérimental), un petit script JS vanilla mesure la hauteur rendue de chaque item et lui pose un `grid-row-end: span N`, calculé sur une unité de rangée fixe (`grid-auto-rows`, constante interne non exposée, ex. `8px`) — recalculé au chargement, après chaque image chargée, et au resize (debounced). Alternative rejetée : une lib JS de positionnement type Masonry.js/Isotope (sur le modèle de Splide pour Carousel), jugée sur-dimensionnée pour un besoin aussi étroit (juste un calcul de span) et qui abandonnerait de toute façon le CSS Grid pour du positionnement absolu en JS pur.

**Mesure de la hauteur d'un item** : avant de mesurer, le JS remet d'abord `grid-row-end` de l'item à une seule rangée (`span 1`), *puis* lit `offsetHeight`. Une boîte de grid item s'étire (`align-self: stretch`, comportement par défaut) pour remplir tout son span courant — la mesurer telle quelle ne révèle donc qu'un agrandissement du contenu (débordement d'une boîte devenue trop petite, visible via `scrollHeight`), jamais un rétrécissement (une boîte devenue trop grande pour un contenu qui a moins besoin de place n'a rien à faire déborder, donc reste figée à son ancienne hauteur). Remettre le span à 1 avant de mesurer effondre la boîte à son plancher de taille naturelle (`min-height: auto` la protège de tout rétrécissement sous son propre contenu), donnant à chaque fois la vraie hauteur au `offsetHeight`, dans les deux sens — y compris quand un padding fluide (`clamp()`) change de valeur au passage d'un breakpoint pendant le resize.

`display: grid` est posé avec `!important` : le support de layout natif de WordPress (ex. `body .is-layout-flex` généré pour `core/gallery`) a une spécificité CSS supérieure à `.blockshifter-masonry` seule et remettrait sinon le bloc en `flex`, désactivant silencieusement le packing.

**Largeur des items sur `core/gallery`** : `.blockshifter-masonry > * { width: auto !important; }` neutralise la règle native de WordPress qui pose sur chaque item un `width: calc(N% - …)` (pensée pour son layout flex d'origine, où ce pourcentage se résout contre la largeur totale de la gallery). Sous notre grid, le containing block d'un item pour la résolution de pourcentage est sa propre colonne — déjà divisée par le nombre de colonnes — donc ce même pourcentage divise la colonne une seconde fois : les images se retrouvaient à une fraction de la taille voulue (ex. ~65px au lieu de ~320px sur une gallery à 4 colonnes de 1340px). Cette règle native a un sélecteur de force ID (`:not(#individual-image)` compte comme un ID en spécificité CSS), donc seul `!important` la bat de façon fiable.

Les réglages `columns` et `gap` divergent entre les deux blocs cibles, parce que `core/gallery` expose déjà ses propres contrôles natifs (Colonnes dans la barre d'outils, espacement dans le panneau Dimensions via son support `spacing.blockGap`) alors que `core/group` n'a d'équivalent pour aucun des deux :

- **`core/group`** garde la config Blockshifter dédiée (`blockshifterConfig.masonry.{columns,gap}`), transmise par le PHP en `--blockshifter-masonry-columns` (custom property, consommée par `grid-template-columns`) et en `gap` directement en style inline (pas d'indirection par custom property : plus simple, et la propriété `gap` est directement ce que le JS doit relire).
- **`core/gallery`** n'a **aucun** contrôle Blockshifter pour `columns`/`gap` dans l'inspecteur (juste le toggle "Enable Masonry mode", avec un texte d'aide renvoyant vers les réglages natifs) : le PHP lit l'attribut natif `columns` du bloc (fallback à 3 s'il est vide — la gallery n'a pas de valeur par défaut, c'est un mode responsive automatique que masonry ne réplique pas) pour poser `--blockshifter-masonry-columns`, et n'écrit **aucune** déclaration `gap` — la règle de style générée nativement par WordPress pour le `blockGap` de la gallery continue de s'appliquer sans conflit, puisque masonry ne touche qu'à `display`.

Le JS lit le gap effectif via `getComputedStyle( grid ).columnGap` (valeur toujours résolue en px par le navigateur), pas via une custom property Blockshifter — ça fonctionne à l'identique que le `gap` vienne du style inline (`core/group`) ou de la règle native WP (`core/gallery`), sans branchement JS par type de bloc et sans dupliquer la valeur entre deux sources.
