# Masonry en CSS Grid + calcul JS des spans, pas de lib tierce ni de CSS columns

Le Module Masonry cible `core/gallery` et `core/group` (comme Carousel) et expose deux réglages : `columns` et `gap`. Le layout est du CSS Grid natif (`grid-template-columns` + `grid-auto-flow: dense`), pas du CSS `columns` (multi-colonnes) : `columns` produit un vrai masonry 100% CSS mais remplit les colonnes verticalement (item 1, 2, 3 empilés avant de passer à la colonne suivante), ce qui casse l'ordre de lecture naturel gauche-à-droite du contenu. Comme CSS Grid seul ne fait du vrai masonry (packing par hauteur réelle) qu'avec `grid-template-rows: masonry` (support navigateur encore expérimental), un petit script JS vanilla mesure la hauteur rendue de chaque item et lui pose un `grid-row-end: span N`, calculé sur une unité de rangée fixe (`grid-auto-rows`, constante interne non exposée, ex. `8px`) — recalculé au chargement, après chaque image chargée, et au resize (debounced). Alternative rejetée : une lib JS de positionnement type Masonry.js/Isotope (sur le modèle de Splide pour Carousel), jugée sur-dimensionnée pour un besoin aussi étroit (juste un calcul de span) et qui abandonnerait de toute façon le CSS Grid pour du positionnement absolu en JS pur. `columns` et `gap` sont transmis en CSS custom properties inline sur la racine (`--blockshifter-masonry-columns`, `--blockshifter-masonry-gap`), consommées nativement par le CSS et relues par le JS via `getComputedStyle()` — une seule source de vérité, contrairement à un `data-*` JSON (comme `data-splide` de Carousel) qui aurait dupliqué `gap` entre JSON et style inline.
