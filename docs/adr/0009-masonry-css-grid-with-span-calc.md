# Masonry en CSS Grid + calcul JS des spans, pas de lib tierce ni de CSS columns

Le Module Masonry cible `core/gallery` et `core/group` (comme Carousel). Le layout est du CSS Grid natif (`grid-template-columns` + `grid-auto-flow: dense`), pas du CSS `columns` (multi-colonnes) : `columns` produit un vrai masonry 100% CSS mais remplit les colonnes verticalement (item 1, 2, 3 empilés avant de passer à la colonne suivante), ce qui casse l'ordre de lecture naturel gauche-à-droite du contenu. Comme CSS Grid seul ne fait du vrai masonry (packing par hauteur réelle) qu'avec `grid-template-rows: masonry` (support navigateur encore expérimental), un petit script JS vanilla mesure la hauteur rendue de chaque item et lui pose un `grid-row-end: span N`, calculé sur une unité de rangée fixe (`grid-auto-rows`, constante interne non exposée, ex. `8px`) — recalculé au chargement, après chaque image chargée, et au resize (debounced). La mesure utilise `scrollHeight`, pas `offsetHeight` : une fois le grid "packed", la boîte de l'item est déjà contrainte par son précédent `grid-row-end`, donc `offsetHeight` ne fait que relire cette valeur figée au lieu de la hauteur naturelle (potentiellement débordante) du contenu — un bug réel rencontré en pratique au resize. Alternative rejetée : une lib JS de positionnement type Masonry.js/Isotope (sur le modèle de Splide pour Carousel), jugée sur-dimensionnée pour un besoin aussi étroit (juste un calcul de span) et qui abandonnerait de toute façon le CSS Grid pour du positionnement absolu en JS pur.

`display: grid` est posé avec `!important` : le support de layout natif de WordPress (ex. `body .is-layout-flex` généré pour `core/gallery`) a une spécificité CSS supérieure à `.blockshifter-masonry` seule et remettrait sinon le bloc en `flex`, désactivant silencieusement le packing.

Les réglages `columns` et `gap` divergent entre les deux blocs cibles, parce que `core/gallery` expose déjà ses propres contrôles natifs (Colonnes dans la barre d'outils, espacement dans le panneau Dimensions via son support `spacing.blockGap`) alors que `core/group` n'a d'équivalent pour aucun des deux :

- **`core/group`** garde la config Blockshifter dédiée (`blockshifterConfig.masonry.{columns,gap}`), transmise par le PHP en `--blockshifter-masonry-columns` (custom property, consommée par `grid-template-columns`) et en `gap` directement en style inline (pas d'indirection par custom property : plus simple, et la propriété `gap` est directement ce que le JS doit relire).
- **`core/gallery`** n'a **aucun** contrôle Blockshifter pour `columns`/`gap` dans l'inspecteur (juste le toggle "Enable Masonry mode", avec un texte d'aide renvoyant vers les réglages natifs) : le PHP lit l'attribut natif `columns` du bloc (fallback à 3 s'il est vide — la gallery n'a pas de valeur par défaut, c'est un mode responsive automatique que masonry ne réplique pas) pour poser `--blockshifter-masonry-columns`, et n'écrit **aucune** déclaration `gap` — la règle de style générée nativement par WordPress pour le `blockGap` de la gallery continue de s'appliquer sans conflit, puisque masonry ne touche qu'à `display`.

Le JS lit le gap effectif via `getComputedStyle( grid ).columnGap` (valeur toujours résolue en px par le navigateur), pas via une custom property Blockshifter — ça fonctionne à l'identique que le `gap` vienne du style inline (`core/group`) ou de la règle native WP (`core/gallery`), sans branchement JS par type de bloc et sans dupliquer la valeur entre deux sources.
